# Database and migration conventions

PostgreSQL 18.6 is pinned by image digest in [Compose](../compose.yaml). Use python scripts/dev.py up from the repository root. The runner generates ignored local random credentials; the container's first initialization creates separate waba_migrator, waba_runtime and NOLOGIN waba_authorizer roles. Existing volumes are never reinitialized or silently assigned new passwords. Stop with python scripts/dev.py down; data remains.

Run python scripts/dev.py migrate. The migration CLI uses Goose 3.28.0, pgx 5.11.0 and a PostgreSQL advisory session lock; only waba_migrator may migrate. It does not run on API startup. Successful repeat applies zero migrations. Each integration run creates its own random test database, applies the same SQL twice, seeds synthetic identities using an isolated setup administrator, asserts through a real waba_runtime connection, then drops that test database. It cannot target the persistent waba database for cleanup.

Migration names are zero-padded ascending numbers plus purpose: 00001_identity_tenants.sql. Goose transactions are the default. Nontransactional operations need explicit NO TRANSACTION annotation, reviewed failure/resume procedure and separate rollout (e.g. concurrent index creation). Update manifest.sha256 only for new unpublished migrations; published SQL is immutable. Forward migrations perform repairs; the initial Down explicitly fails. Never auto-sync a schema. Destructive changes require separate expand/backfill/contract releases and backup/rollback evidence.

The current binary requires schema version 1 exactly; readiness rejects both older and newer versions. Future expand releases must widen this range explicitly and test old/new binaries before rollout. Migration IDs are not an exactly-once external-effect guarantee.

Implemented tables: app.users, app.organizations and app.organization_members, plus Goose metadata. Passwords, sessions, invitations, roles/grants and business modules remain later-sprint work. UUIDv7 comes from google/uuid, never a custom generator. Composite (organization_id,id) keys establish the convention for future tenant FKs.

The runtime owns no tables, has no BYPASSRLS/superuser/create-role/schema-write capability and cannot read global users. Organization/member tables FORCE RLS with missing-scope deny. InOrganization checks an active server-authenticated user/member/organization before set_config(...,true) inside the same transaction; it always commits or rolls back before pool reuse. It is an internal boundary, not authentication: never supply user identity from a header or request parameter. No tenant routes exist in Sprint 0.

A narrow SECURITY DEFINER function owned by NOLOGIN waba_authorizer performs the pre-scope lookup and holds SHARE locks on identity/membership/organization. It has fixed search_path, fixed SQL and no public EXECUTE. Its row-visibility policy permits locks but WITH CHECK false and limited grants deny business writes. waba_runtime cannot SET ROLE to this role. This is not a general privileged SQL function. Direct SQL may set a custom tenant GUC; RLS is defense in depth against missing/wrong scope, not protection from fully compromised trusted application code/DB credentials. The application membership check remains mandatory.

Local Compose plus unique disposable databases was chosen over Testcontainers to reuse exactly the same pinned server in development and CI, with no extra test orchestration dependency. Infrastructure must be running; explicit integration execution fails when configuration/PostgreSQL is missing and never silently skips. Global setup administrator credentials exist only in this isolated test harness, not the API process.
