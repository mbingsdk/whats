# Database design

PostgreSQL is the source of truth. This is the full target logical schema. Migrations 00001 and 00002 implement the identity subset described in [Sprint 1 evidence](24-sprint-1-evidence.md). The remaining business schema below is a future target. Concrete identity names differ where normalized: password_identities stores the credential hash; role_permissions/member_roles/team_roles store grants; audit_log and identity_audit separate tenant and global security events. IDs use UUIDv7 generated by the application; external Meta IDs remain text. No integer parsing assumptions for Graph IDs or `wamid` values.

## Conventions that apply to every table below

`T` means tenant table: `id uuid PK`, `organization_id uuid NOT NULL FK organizations`, `UNIQUE(organization_id,id)`, `created_at timestamptz NOT NULL`. Mutable T tables also have `updated_at` and `revision bigint NOT NULL DEFAULT 1`. `A` means append-only T table: no updated_at/revision, only explicit correction rows. `G` means global security/catalog table with an explicit exception described below. Every column listed is NOT NULL unless suffixed `?`. `jsonb` is schema-versioned and size-limited, not an excuse to avoid keys. `ref` means a composite `(organization_id, target_id)` FK unless global target is stated. Every FK's referencing columns get a B-tree index unless covered by a listed leading index. No automatic CASCADE from users/members or organizations to business/audit data.

All T/A tables use FORCE ROW LEVEL SECURITY for the app and worker roles and a transaction-local organization setting. App roles neither own tables nor hold BYPASSRLS. USING and WITH CHECK both apply. Migrations use a separate role. RLS does not replace application checks; privileged jobs use narrowly scoped functions for routing then enter tenant context. [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Unless stated otherwise: no soft-delete column; destructive business deletion is denied, historical entities archive via `archived_at?`. Retention workers explicitly purge eligible content after legal-hold/tombstone checks. A table's internal status values come from doc 04 or a closed CHECK named in its row. External statuses are text plus normalized status, observed_at and source. Mutable commands compare revision.

Money uses `numeric(24,9)` plus ISO currency; quantities are integer. Never binary floating point. Store exact rate provenance and rounding policy. Timestamps are UTC; effective intervals are half-open `[from,to)`. Conflicting rate/policy coverage is prevented within each publication by exclusion constraints on publication plus complete dimensional key/range (or a serialized publication check for JSON dimensions). Historical publications can cover the same interval without mutating one another. Unique constraints with nullable values must use partial indexes or NULLS NOT DISTINCT deliberately.

## Critical transaction patterns

Foreign-key example (illustrative only): `FOREIGN KEY (organization_id, conversation_id) REFERENCES conversations(organization_id,id)`. A UUID match alone is insufficient. Circular references such as current_version are added as deferred constraints after both rows exist; cross-table lifecycle checks run in service transactions with necessary row locks.

Final dispatch uses the shared organization barrier and narrower resource locks specified below, under READ COMMITTED. Reserve/consume confirmations, monetary authority and frequency in that transaction. No network calls, media work or audience computation while holding these locks; revalidate again when moving a reserved intent into DISPATCHING.

Job claim uses a small ordered batch with `FOR UPDATE SKIP LOCKED`, lease token increment, then commit. A stale worker cannot commit local results without its fence. Any lease recovery finding DISPATCHING treats external outcome as uncertain. Never requeue based on expired lease alone.

Partitioning is DEFERRED initially: time partitioning messages would complicate global external-ID uniqueness. If needed, retain unpartitioned identity/deduplication tables and partition large history/payload tables separately. Inspect EXPLAIN on seeded realistic tenant distributions before adding indexes. Avoid a global GIN index over PII/raw JSON.

## Dispatch locking: scope, absence checks and contention

The organization barrier protects exactly this invariant: no DISPATCHING authorization committed after an organization-wide disable or relevant policy/access-topology publication may use the previous policy. Ordinary sends hold organization_guards FOR SHARE until commit and never update it. The writer takes FOR UPDATE, changes the flag/revision and commits; compatible send readers can overlap. FOR KEY SHARE is insufficient because it need not conflict with non-key updates. This is a row-lock protocol, not a global mutex. [PostgreSQL row-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html).

Canonical order, sorting IDs within each tier: global user principals FOR SHARE; organization_guards FOR SHARE; current memberships/sessions/API keys and relevant app/WABA/phone/template/automation configuration FOR SHARE; campaign/run FOR SHARE; recipient_guards FOR UPDATE; contacts FOR UPDATE; conversations FOR UPDATE; applicable budget definitions FOR SHARE; budget_periods FOR UPDATE for positive exposure (FOR SHARE for verified zero-cost read-only checks); approval requests/authorities and pricing authorization FOR SHARE when read-only, FOR UPDATE when consuming/reserving; intent/attempt/effect rows. Only acquire relevant rows. Compute candidate IDs before locking, reread all predicates after locks and restart if membership of the lock set changed; never acquire a newly discovered earlier-tier lock out of order. No SHARE-to-UPDATE upgrade: writers choose their stronger mode at entry.

| Concern | Writer and dispatch ordering |
| --- | --- |
| Emergency disable/global pricing, consent or frequency policy; role/team grant topology | Writer locks organization barrier exclusively first (after any global-user lock); publish revision/pointer atomically. Numeric per-contact changes do not update this row. |
| Existing membership/session/key or asset/template status | Writer locks affected row exclusively; sender holds it shared. Role/team topology changes additionally use org exclusive barrier, protecting newly matching grants. |
| Consent/suppression and frequency | Sender and opt-out writer lock stable recipient anchor then contact, not organization exclusively; frequency reads/reservations serialize on that contact. Even absence of a suppression row is protected. |
| Conversation/assignment/handoff/window | Lock contact before conversation whenever both are needed, including inbound projection. Takeover can lock conversation alone under org shared barrier; it must not later acquire an earlier-tier contact lock. |
| Campaign pause/cancel | Run FOR UPDATE conflicts with dispatch FOR SHARE. Recipient progress writes recipient/outbox only; counters aggregate after dispatch, never upgrade the run lock on every send. |
| Budget limits and periods | Existing numeric-limit writer locks budget definition FOR UPDATE then periods; sender holds definition shared then atomically updates periods. New/enabled/removed/re-scoped budgets take org exclusive barrier to protect the matching-budget set against phantoms. |
| Financial approval/confirmation | Lock immutable request/current authority and consume/reserve under its authority row. Revocation uses the same order. Per-campaign shared cap is a real localized serialization point. |

| Table / kind | Columns | Invariants |
| --- | --- | --- |
| recipient_guards T | namespace, identifier_lookup_hmac, lookup_key_version, canonical_guard_id? ref recipient_guards, contact_id? ref | U(org,namespace,identifier_lookup_hmac,lookup_key_version). Upsert before send/opt-out even without contact. Null canonical_guard_id means root; aliases point directly to a same-org root (no chains/cycles), enforced by locked writer checks. Lock the resolved root ID; key rotation publishes digest aliases under org exclusive barrier, never creating an independent consent anchor. |

Every possible outbound target resolves an anchor before evaluating suppression. An opt-out for an unknown identifier creates it too; uniqueness serializes concurrent creation. Known aliases additionally converge on the same locked contact. Contact/identity merge or relink locks all affected anchors then contacts in sorted order and rechecks mappings before commit. Ordinary inbound message projection uses these anchors without an exclusive org lock; raw durable ingress does not acquire a dispatch barrier at all.

Contention is still possible: one funded organization budget period necessarily serializes positive reservations, a run-wide authority serializes that cap, and a busy contact/conversation serializes its own changes. Keep these sections short and reserve late; do not claim narrower org locking removes all hot rows. SSE publication sequence is another separately measured row, outside the dispatch transaction.

Analytical baseline only: an exclusive org lock held h milliseconds permits at most about 1000/h authorizations per second before other work; h=5/10/20 ms implies ideal ceilings 200/100/50, not measured throughput. Holding that lock while waiting on a budget or conversation would make the ceiling worse. The shared barrier removes ordinary reader-reader serialization, while broad policy writers can briefly block a cohort.

Gate for retaining this design: doc 17's mixed-load benchmark must measure per-tier wait/hold p50/p95/p99, throughput and queue age. Proposed review thresholds are final-authorization p95 <=50 ms/p99 <=200 ms, org-shared wait p99 <=20 ms outside declared policy-write intervals, and committed emergency disable/opt-out/pause latency p99 <=1 s. Failures over five sustained minutes at accepted workload, unbounded backlog or writer starvation require redesign before release. Cap transaction/lock waits at 250 ms with bounded jittered retry and interactive priority; a timeout grants no permit. If a real shared budget remains limiting, review bounded sub-reservation allocations with conserved totals rather than weakening spending invariants. No benchmark has run in this phase.

## Sprint 1 physical schema decisions

Migration 00002 adds nine organization-owned FORCE-RLS tables and eleven explicitly global identity/catalog/mail tables, plus users.verified_at. sessions.access_revision binds an organization session to the live membership revision; a NULL organization permits only identity operations until membership is selected. Dedicated NOINHERIT waba_identity has global identity DML, append-only audit access and scoped tenant DML; waba_runtime still cannot read users/passwords/sessions. Both roles remain non-owner and NOBYPASSRLS. Authorizer functions have fixed SQL/search_path and no public EXECUTE.

Role topology writers lock the organization exclusively; readers hold its shared barrier through authorization. Mutations compare revisions, enforce delegation ceilings and retain at least one active organization-wide owners.manage grant. Affected membership access revisions invalidate old organization sessions; global auth_revision changes invalidate all sessions. Invitation acceptance discovers and locks recipient/inviter user IDs in sorted order before the organization barrier. Identity volume is intentionally serialized per user and per organization writer; this is not dispatch throughput evidence.

Global mail_deliveries/mail_attempts are accessible only to the identity service. An invitation delivery has an organization+invitation composite FK; tenant HTTP reads filter both IDs and expose only sanitized delivery state. Token-bearing payloads are envelope encrypted and purged on terminal delivery. Template version 1 is explicit; completed attempts are protected by an immutable-row trigger. Audit records store stable actors, a label snapshot, action/resource/revision, request ID, UTC time and a change digest rather than raw secret-bearing input.
